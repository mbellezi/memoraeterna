# F2 decisions: Topic Tree Engine (2026-10-15)

Binding design decisions for phase F2 (`docs/plan.md` decision 18). The plan holds the F2 task boxes, waves and
exit criteria; this file records how and why the engine is built that way. Values marked *(cal.)* are start
values that calibration (T29a, T29b) confirms or revises on measured data. "Q" marks an owner question: each has
a default, and work proceeds on the default until the owner answers. The profiles (ENV-G, ENV-F, ENV-C) and
the exit criteria E1-E6 are defined under Measurement. Spike B start values: `docs/spikes/spike-b-topic-tree.md`.

## Decisions

| # | Decision | Why / alternative rejected |
| --- | --- | --- |
| D1 (Q1) | **Topic identity lives in a new table, `topics`**, and `topics.parent_id` is its only parent pointer. `wiki_pages` stays legacy like every other wiki table: emptied at the switch, dropped in F4. Plan 4.1 "Ownership" and "Data" are reworded to say this. | A shadow tree cannot live in `wiki_pages`: the curator, maintenance, the Wiki screen, Obsidian and KPI read it, and its triggers fire. Its TOC columns could only change after the wipe. Engine FKs into a legacy table break the wipe's `TRUNCATE`. Single-writer safety would depend on finishing the deletion first. The alternative costs about 2 d plus a second gated step. |
| D2 | **Modes per profile.** **Active:** the marker `topics.mode.v1` exists, or the profile has no legacy content, in which case the marker is set at startup or after a reset with `reason: "empty"`. **Legacy:** legacy content exists. The service then keeps a **shadow tree**: deterministic placement only, no generative calls, visible only in developer exports. Legacy content means rows in `wiki_pages`, `organization_runs`, `organization_settings_revisions`, `maintenance_runs`, `maintenance_schedules`, `wiki_policy_revisions` or `wiki_investigations`. The trigger-fed `knowledge_impact_*` rows do not count. | Scratch, fresh and reset profiles run the real engine early; the owner's legacy profile is untouched until the switch. |
| D3 | **Legacy state is never created from nothing** (T04). `initializeAutomation` runs only when legacy content exists. Full-knowledge admission records `organizeKnowledge` as skipped when no curator policy exists. | Without this, every reset re-creates the legacy wiki (library reset runs `initializeKnowledgeDefaults`, whose `initializeAutomation` recreates the 9 area pages and the curator policy), and the zero-config e2e test fails. |
| D4 | **The wipe is a gated, idempotent, checkpointed service step** (`TopicSwitchService`), never a migration. The steps are: quiesce, snapshot counts, `pg_dump --snapshot`, verify by restore, one wipe transaction, bootstrap. Checkpoints resume a crash and a marker prevents a rerun (T36; rehearsed on a restored copy in T37). | A migration runs at every start with no backup, and would wipe any restored backup opened later. |
| D5 | **The 22 legacy impact triggers, their 4 functions and the FK `atomic_note_evolution.run_id → organization_runs` are dropped by a migration that keeps all data** (T35), before the switch. `invalidate_obsidian_projection` stays. | It removes per-row writes on the ingestion hot path, and the `TRUNCATE` cannot fail on FKs or late-bound plpgsql. |
| D6 | **The legacy tables are emptied in F2 and dropped in F4.** `schema.ts` keeps them until then. | Plan F4; `rules/data.md`. |
| D7 | **Statistics are derived and exact.** Per topic, the stats are `n`, `ls` (Float64 `bytea`), `cos_sq_sum` and the low-cosine percentiles. After any placement change, the touched path is recomputed bottom-up: a leaf is the sum of its members' current vectors, in content-key order; an internal node is the sum of its children's `ls` plus its direct items. In-memory add/subtract is used only inside one engine run and in replay. A member whose vector is missing or stale (an edit pending re-embedding) keeps its placement and is left out of the stats until its new vector exists. Internal nodes sum children in `topics.id` order, so the recompute is bit-stable. Deleted items leave through D32. | The subtract path would need the old vector, which an edit deletes. A per-placement vector copy costs 4 KiB per item and duplicates canonical data. |
| D8 | **Items and counting.** Notes and root sources are both items (I1). `n`/`ls` count notes. A root source counts only while it has no current placed note. Leaf size (I4) counts direct items of both kinds. **Root vector:** `unit(Σ max(0, v·m)^2 · v)` over the root's current notes, with one refinement pass. The fallback is the stored `source-composite-centroid-v2` vector. With neither, the source waits in Unsorted with `needs_vector`. A root is re-placed only when its vector cosine to the last placed vector drops below `items.sourceReplaceCosine` (0.98, *cal.*). | No double counting; a source with no notes stays reachable; no metadata vector is stored to fall back on. |
| D9 | **The single writer is enforced twice.** (1) A `BEFORE INSERT OR UPDATE OF parent_id, management` trigger on `topics` rejects an AI-managed write unless the transaction set `memora.topic_writer = 'engine'`. (2) A static test allows only `topicTreeRepository.ts` to write the **structure tables** (`topic_trees`, `topics`, `topic_stats`, `topic_placements`, `topic_change_sets`, `topic_structure_events`) and its own logs (`topic_gate_decisions`, `topic_daily_metrics`, `topic_calibrations`). Other writers are explicit: `topicOverviewRepository.ts` owns the overview tables; the switch retires shadow trees by calling `topicTreeRepository` with its transaction client; DEV seeders and verify scripts write through `topicTreeRepository` (no raw SQL); the only database-side write is D32's cascade and dirty flag. | "Enforced by test" (plan), plus raw SQL in scripts. |
| D10 | **Placement never waits for AI.** `decidePlacement` returns `auto` (best leaf, margin ≥ θm), `gate` (≤5 candidates plus the deepest admitted common ancestor) or `unadmitted` (an ancestor). For `gate`, the item is applied at the fallback ancestor with `needs_gate` and a deduped `topic-gate` job is enqueued. **The gate rule:** only a **validated dedicated ranker** decides; there is no generative gate. Compute `p = softmax([logOdds…, τ]/T)`; accept the best candidate when p ≥ θ, otherwise "none" (`needs_split_check`). With no validated decide route, `needs_gate` stays set, and `topic-sweep` re-enqueues the item once a route validates. Start values: margin 0.015, T 1, τ 0, θ 0.5, label weight 0. PLACE runs on the light lane's `compute` worker and the gate on its `model` worker (D33), so a gate call waiting for the AI slot never holds a placement. | Spike B: 30-50% of new-topic notes are ambiguous. A gate call queued behind a multi-minute heavy call would stall PLACE. |
| D11 | **Naming.** Operation `topic_name`, class `write-fast` (task `structured-output` when no class route exists). At most 24 topics per call, parent first, aliases in content-key order. The schema has a `language` field that must equal the content language. Validation: not equal to the parent, unique among siblings (accent- and case-insensitive), no ID-shaped strings. One repair re-asks only the invalid items (the F1a matching precedent, applied inside the topic service; the F3 runtime-wide rule is not implemented here). Then a provisional TF-IDF name from content-language notes only, with stopwords for 5 languages. Otherwise `title = null`, `name_state = 'unnamed'`, and the UI renders the localized "Unnamed topic"; no placeholder is stored. **Re-naming happens only** on create, split or merge, or when membership drift since naming is ≥ `naming.renameDrift` (0.3, *cal.*). Human-named topics are never renamed. | Plan 4.1 Naming; Spike B 23/30 names; stability of names. |
| D12 | **Areas** (the top two levels). An LLM proposes a Clio-style grouping of the level-2 topics into 7-16 Areas (target 10, *cal.*; the plan's earlier "~10-16" is re-based on Spike B's 7-12), with pinned Areas fixed. Code validates it: every topic exactly once, size bounds. It is accepted only when the mean silhouette of the level-2 centroids under the proposal is not lower than under the current grouping (tolerance *cal.*) and the E2 shape bars still hold. It applies automatically at bootstrap; afterwards **every Area-level operation** (Area regrouping, and any REBALANCE split, merge, dissolve or push-down that changes the set of level-1 topics) becomes `pending_review` (plan 4.3). The root's fan-out band is the Areas band, not I3, so REBALANCE never pushes Areas down. The mis-parent audit is deterministic and goes through REBALANCE acceptance. | Spike B: level 1 was 1/4 coherent and seed-dependent. |
| D13 (Q2) | **Ask is decoupled from the wiki in wave 2.** It retrieves from notes and chunks only, with no domain or page scope, no "save answer as page" and no followed questions. A topic-subtree scope arrives in T28. Organization domains are dropped. | They write `wiki_pages` through the organization stack, which is deleted. Questions arrive in F5. |
| D14 | **`organizeKnowledge` leaves the processing DAG at the detach (T35).** Stored plans, runs and batches are read tolerantly: legacy stage IDs read as "skipped (retired)", and the `integrateWiki`/`organization` fields are dropped when parsed. | Admission would throw once the policy is wiped; history must still parse. |
| D15 | **Push channels.** `topicsChanged {treeId, generation, topicIds≤200\|null, changeSetId}`, coalesced over 250 ms after commit, and `topicsSwitchProgress`. They follow the `jobsChanged`/`viewHistoryChanged` precedent; the F4 event bus can absorb them. No new polling. | `rules/frontend.md`, `rules/architecture.md`. |
| D16 | **Overviews get their own tables** (`topic_overviews`, `topic_overview_citations`). They are written when the page is opened and cached per member fingerprint, prompt revision, model and language. | The legacy revision tables carry the trigger family and duplicate `parentId`. |
| D17 | **"decide" means a validated dedicated ranker.** It keeps the `reranking` capability. Generative catalog entries lose the `reranking` tag, and `hasGeneration` stops counting it. The validation is stored per install in `local_models.metadata.decideValidation` (artifact SHA-256, runtime build, smoke result, time), and a revision or artifact change invalidates it. `supportsTask` is unchanged. | It is the smallest change that makes code and rule agree. |
| D18 | **No new AI scheduler in F2.** Route order: operation override (`op:<operation>`), then the class route (`class:<class>`) **only when the request sets `workloadClass` explicitly**, then the task route. `class:decide` is seeded only from a validated ranker, the MLX ranker first when the host runs MLX, else the GGUF one (decision 12); `class:write-fast` from the writer route, under the privacy rule. **Minimal residency, pulled from F3 (Q11):** one MLX helper process holds at most one `generate`, one `embed` and one `score` model; `AiService` keeps one embedding and one ranker adapter resident beside the one generative adapter; rankers are exempt from idle release, like embeddings. Idle unload of the generative model and group sizing stay in F3. Light-lane AI calls use the existing `background` queue class. | A third queue class gains nothing while the heavy lane issues one call at a time. Real lanes are F3. Without residency every gate call between embedding calls reloads both models. |
| D19 | **The ambiguity bar is re-based** (Spike B condition 5). The bars *(cal.)*: (a) auto-placement precision ≥90% on known topics; (b) of new-topic notes, ≤50% gated; (c) gate p95 ≤0.3 s per gated note (target 0.2 s). Gate precision on new topics is reported against the margin-only baseline. | The 30% bar measured gate capacity, not quality. |
| D20 (Q3) | **Owner rating rule:** a topic counts only if rated **both** coherent and well named, and the bar is ≥24/30 such topics. The two marginals are reported. | It is the literal reading of the exit text, and it is conservative because it gates the wipe. |
| D21 | **Developer comparison panel:** a generated HTML report (`npm run topics:report`). It reads `.f32` replays and in-app `topics:export` JSON, never a live owner database. | No product copy, IPC or i18n for developer tooling. |
| D22 | **Determinism by content key.** Clustering rows, prompt aliases, gate candidate order and stats summation follow note content hash, then ID. | `rules/ai.md`: prompts are a function of content. Cassette keys and the rebuilt tree must be stable across replays with fresh UUIDs. |
| D23 | **G1: `MEMORA_GOLDEN_TOPICS=deterministic\|full`, read only when `MEMORA_GOLDEN_RUN` is set.** Every non-golden run (DEV, packaged, E6) behaves as `full`. In a golden run the default `deterministic` places and rebalances but makes no topic AI call (no gate, naming, Areas, labels or overview). F2 measurements use `full` in `record` mode on cassette copies. **Topic barrier:** in `full` golden runs, ENV-C seeding and the E6 harness, topic jobs are held while a source ingests and the light lane is drained at each source boundary (or once at the end with `MEMORA_GOLDEN_TOPICS_ARRIVAL=batch`), so the items present at every build and naming call are a function of the manifest order. `per-source` is the default arrival in `full` runs. | Existing replays (F1b/F3) keep 0 misses and their timing; recorded `topic.*` calls replay at 0 misses. |
| D24 | **`objects.locate`:** `primaryPath` = the topic ancestors (root to primary topic) followed by the existing source chain; `alsoIn` = secondary placements (≤2); `citedBy` = overviews that cite the object; the `legacy` flag goes. | The F1b contract comment announced this shape (`object-address.ts`). |
| D25 (Q9) | **No MLX embedding adapter in F2.** The engine uses stored note vectors in the active route's space. T01's protocol supports `embed`, so F3 can add the adapter. | A new space forces a library re-embed; MLX and GGUF vectors agree at cosine 0.9996. |
| D26 (Q8) | **Embedding space.** A pure `embeddingSpaceKey(selection, adapterIdentity)` is extracted from `ai-service.ts`. `activeEmbeddingSpace()` computes the route's space **without a call** and confirms it against the newest stored note vector. When the tree's space differs from the route's, the status is `space_changed`: PLACE of new-space items waits, and current notes are re-embedded through the existing `note-embedding` jobs (automatically for local routes; through an explicit action for remote routes). At ≥95% coverage *(cal.)* the tree rebuilds in the new space and is mapped by Hungarian matching. Spaces are never compared. | `rules/data.md` vectors rule; plan 4.1. |
| D27 | **Unsorted.** In the navigator, "Sem lugar / Unsorted" is the direct items of the root. An item waiting at an internal ancestor with `needs_gate` or `needs_split_check` is shown in that topic's item list with an "unsorted" marker. The **Unsorted share KPI** counts both groups; roots waiting with `needs_vector` (import-only sources, catalog containers without text) are reachable but reported apart, not in the share. Ordinary direct items of an internal topic (the mockup's "2 + 6 diretos") are not unsorted. | Mockups `Topic.dc.html` ("Sem lugar 3") and `Map.dc.html` ("1,9%", "2 + 6 diretos"). |
| D28 (Q5) | **Pin.** Pinning a topic is one user action with two effects in one change-set: a `view_history` pin (the navigator's "Fixados / Pinned") and `topics.management = 'pinned'`, which protects the topic. Pinning a note or source only touches `view_history`. Protection is read from `topics.management` only. Undoing a pin or unpin change-set restores both effects in one transaction. | One canonical protection flag; "pinned nodes never move automatically" (plan 4.1). |
| D29 (Q10) | **`pending_review` change-sets** (protected structure, Area regrouping, high-risk rebuilds or merges) are listed in Shape warnings with Apply and Dismiss in F2. The mockup's "Abrir na Inbox" lands with the F4 Inbox. | Without it, proposals accumulate with no resolution. |
| D30 | **Obsidian projection runs on the light lane**, delivered in pages with a persisted checkpoint. `applyChangeSet` bumps `obsidian_projection_clock` explicitly, and only for the active tree. The topic tables get no projection triggers. | Shadow trees must not re-run projections; plan 4.3 puts projection in the light lane. |
| D31 | **Migrations take the next free number at generation time**, with one owner at a time (`RULES.md` section 5). | — |
| D32 | **Deleted items leave by cascade.** `topic_placements.note_id` and `source_item_id` are `ON DELETE CASCADE`. A statement-level `AFTER DELETE ... REFERENCING OLD TABLE` trigger on `topic_placements` sets `topic_stats.dirty = true` for the affected topics and their ancestors (a stats flag; D9's guard is untouched). `topic-sweep` (startup, after audits, and when enqueued) recomputes dirty paths and enqueues `topic-rebalance`; the known paths (source deletion, `chunkRepository` replacement, note status and supersession) also enqueue it at once. Structure events keep item IDs without FKs; undoing a change-set that touched a deleted item reports the blocker `itemDeleted`. | Restrict FKs would make reprocessing (re-chunking deletes notes by cascade) and any future delete path fail ingestion; derived stats make the cascade safe. |
| D33 | **The light lane has two workers.** `compute` claims light job types that make no model call (`topic-place`, `topic-sweep`, `topic-rebalance`, `topic-build`, `topic-audit`, `obsidian-wiki`); `model` claims the ones that do (`topic-gate`, `topic-name`, `topic-areas`, `topic-label-embed`). Each type declares `needsModel` in the executor registry, and `claimNext` filters by lane and type set. The heavy lane keeps one worker. | Placement never waits for AI (D10) only if no job that waits for the AI slot sits ahead of it in a one-job lane. |
| D34 | **Bounded background topic AI.** `topics.ai.maxBackgroundCallsPerDay` (typed config, *cal.*, start 300) caps background naming, Areas and label-embedding calls per local day; at the cap, topics keep provisional names, the status says why, and work resumes the next day. Overviews written on open are interactive and not capped. The F4 money cap supersedes it. | Remote routes (Codex OAuth) have no money cap until F4; `RULES.md` asks before expensive actions. |
| D35 | **Proof slots.** A proof that starts the DEV app takes the DEV-app slot; one that runs a local model takes the local-model slot (`waitForLocalModelSlot`). The orchestrator schedules slot holders one at a time; implementation, unit tests and scratch PostgreSQL proofs stay parallel. | One Memora instance and one local inference at a time (`rules/architecture.md`, `rules/ai.md`). |
| D36 (Q12) | **Legacy maintenance v1, routines and the Automation screen are removed in F2** (T38/T39), pulled from F4's "Retire routines, maintenance v1, dead screens". After T35 they are unwired and bound to wiped tables and removed repositories. Legacy tables are still dropped in F4. | Keeping them would force T40 to keep `wikiRepository.save` and other legacy repositories alive for dead code. |

## Measurement

- **Exit criteria E1-E6** are the plan's F2 exit, in order: reachability, shape, churn, owner rating, undo,
  zero-config e2e.
- **Profiles** (under `.cache/profiles/`, reset clones of the DEV profile): ENV-G golden-small (10 roots, 160
  pinned notes), ENV-F matching fixture (60 roots, 138 pinned notes), ENV-C the 18,632-note corpus re-embedded
  through the app's embedding route. ENV-G and ENV-F record topic calls only into cassette copies.
- **Seeds are pre-registered and disjoint:** evaluation (E1-E3, gates A and C) 20261014 and 1-5; calibration
  (T29a, T29b) 7-12. A calibration run never reuses an evaluation seed or split.
- **Readings:** E2 reports the root apart (its band is the Areas band, D12); E3 replay descriptors use the
  content-language TF-IDF name plus 3 central titles, with a gate-off sensitivity run beside it; E6 excludes the
  root from the naming checks and reports the share of notes left there.
- **Reported, not gating:** Unsorted share ≤2% from 50 items (D27, `needs_vector` roots apart); the D19 bars;
  `objects.locate`, `topics.tree` and `topics.page` p95 ≤50 ms and `topics.shape` ≤100 ms; light-lane
  enqueue-to-done p95; the fixture sanity check (expected root pairs share a topic or are siblings more often
  than forbidden pairs); the undo rate of automatic change-sets (≤5%); the days D34's cap was reached.
